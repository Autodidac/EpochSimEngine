# SandHybrid Production Rewrite Plan

## Decision

The current simulation is a useful behavior prototype, not the final production architecture. Repeated fixes across fine cells, 8x8 packets, 64x64 sections, shaders, UI state, and runtime ownership have created overlapping authorities. That is the source of water ownership ping-pong, disappearing half-water, false stable blocks, misleading debug counters, and excessive work on inactive world space.

The rewrite proceeds inside the reusable `SandHybrid::SandHybrid` library. `SandHybrid::VulkanRuntime` remains an optional execution backend and `SandHybrid_Demo` remains a thin native host. The old runtime stays buildable until every migration gate passes; replacement is staged, measured, and reversible.

## Reference model

The section system follows the proven large-world principles presented for Noita's Falling Everything engine:

- 64x64 simulation sections;
- dirty rectangles inside each section;
- non-touching section phases for safe parallel work;
- sparse active-area updates instead of scanning the whole world;
- larger streamed pages around the player, with distant pages saved and unloaded.

SandHybrid keeps its own requirements: conserved half-water, composite atmosphere, structural-tile fracture, wet granular state, industrial machinery, deterministic tests, optional Vulkan acceleration, and cross-platform C++23 library use.

## Non-negotiable ownership rules

1. Canonical cell state is the only material truth.
2. Solid tiles are structural/sleep metadata, never a second movable material representation.
3. At 31 destroyed cells out of 64 (48.4375%), the remaining solid cells release individually.
4. Liquid and gas packets are transient acceleration jobs derived from canonical cells.
5. A packet commits atomically or falls back to fine-cell work in the same tick; it never alternates ownership every frame.
6. Half-water is conserved cell state and cannot be erased by packet classification.
7. Actors and machines use occupancy/components, not material-cell identity.
8. Debug counters are generated by accepted work records, not inferred from colors or classifications.

## Target hierarchy

| Layer | Size | Responsibility |
|---|---:|---|
| Cell | 1x1 | Canonical material, temperature, moisture, composition, damage, and flags |
| Structural block | 8x8 metadata | Support/cohesion/sleep/fracture only; no whole-block solid movement |
| Simulation section | 64x64 | Dirty rectangle, wake/sleep state, phase scheduling, boundary exchange |
| Stream page | 512x512 | Allocation, persistence, compression, loading, and eviction |
| World | sparse | Coordinate mapping and resident-page index; no fixed full-world scan |

## Parallel execution

Each 64x64 section maps to one of four phases using the low bits of its signed coordinates. Sections in the same phase never touch by edge or corner. A tick processes phases in deterministic order; workers consume immutable work batches and return change records. Only the coordinator mutates sparse section metadata between phases.

Boundary changes expand by a one-cell halo and wake neighboring sections for the next phase/tick. A section sleeps when it produces no change, receives no boundary input, and has no pending reaction, pressure, actor, machine, or tool event.

## Migration stages

### R0 - Freeze contracts and measurements

- preserve all current mission IDs and acceptance criteria;
- record CPU time, GPU time, active sections, dirty area, cells tested, cells changed, packet attempts, packet commits, packet fallbacks, boundary wakes, and conservation error;
- add deterministic reproductions for water ping-pong, half-water loss, solid reconstruction, atmosphere fill, and machine routing.

### R1 - Library boundary

Completed by the reusable-library branch:

- platform-neutral static core target;
- optional Vulkan runtime target;
- thin demo/native host;
- installed CMake package and downstream consumer test.

### R2 - Sparse section metadata

Initiated in v2.5.0:

- `SparseSectionGrid` with signed world coordinates;
- 64x64 sections and local dirty rectangles;
- four non-touching phases;
- halo wakeups, sleeping, and clean-metadata retirement;
- 512x512 stream-page constants;
- deterministic contract tests.

Acceptance requires integrating the grid with simulation dispatch so clean sections execute zero material work.

### R3 - Canonical cell storage

- replace duplicated material authority with one cell store;
- use structure-of-arrays pages for hot fields and optional cold sidecars;
- append-only material IDs and explicit save schema versioning;
- preserve half-water, wet-material, atmosphere-component, and damage state exactly.

### R4 - Transactional liquid/gas acceleration

- discover eligible full 8x8 regions from canonical cells;
- calculate packet transfer into a scratch transaction;
- validate destination, conservation, boundaries, and reactions;
- atomically commit or execute fine fallback immediately;
- require packet/fine parity tests for every eligible material class.

### R5 - Structural solids

- keep structural occupancy/support metadata separate from cell movement;
- preserve authored blocks while supported;
- accumulate exact cell damage;
- release remaining cells individually at the 48% destroyed threshold;
- never reconstruct released stone or metal from a stable-section flag.

### R6 - Atmosphere and pressure

- pack N2/O2/Ar/CO2/H2/He/vapor/contaminants in canonical atmosphere cells;
- treat visible excess gas as conserved transport, not replacement material;
- use section boundary exchange for pressure/composition;
- prove closed-box conservation and equilibrium.

### R7 - Actors and machinery

- move player, insects, conveyors, sluices, smelters, assemblers, vents, and habitats to component/occupancy systems;
- machines consume explicit input cells and emit explicit output cells through configurable ports;
- conveyors and sluices expose deterministic direction/output-side state;
- no machine action may be hidden inside generic material swapping.

### R8 - Streaming world

- allocate sparse 512x512 pages around active cameras/players;
- maintain explicit resident, dirty, saving, unloaded, and generated states;
- save distant modified pages asynchronously;
- load boundary neighbors before allowing cross-page transfer;
- support larger worlds without allocating every cell.

### R9 - Vulkan backend rewrite

- consume section work batches and immutable page views from the core;
- dispatch only dirty rectangles;
- keep CPU reference execution for parity and fallback;
- separate simulation, debug generation, and presentation timings;
- remove shader-owned world policy.

### R10 - Cutover and deletion

- run old/new engines side by side on deterministic scenes;
- compare material totals, atmosphere components, heat, moisture, machine outputs, and actor state;
- require Windows/Linux Release builds and old-hardware performance targets;
- switch the demo only after visual/runtime acceptance;
- delete old hierarchy shaders and compatibility code after the replacement release proves stable.

## Performance gates

- clean sections perform zero cell or packet tests;
- active work scales with dirty area rather than resident-world area;
- no main-thread simulation work;
- no per-tick heap allocation in the final scheduler path;
- no full GPU buffer clear/readback for inactive sections;
- one million active cells must have a published CPU/GPU timing baseline;
- large mostly-static worlds must remain practical on older four-core systems and integrated/discrete GPUs supported by the Vulkan backend.

## Release policy

A release may include rewrite foundations before full cutover, but release notes and `missioncache.md` must state exactly which migration stage is active. Compilation or static contracts never close runtime missions. Failed, deferred, or unverified behavior remains in the canonical mission cache.
